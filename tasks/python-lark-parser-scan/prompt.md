I'd like Lark to be able to find grammar matches inside a larger text, the way a regex search would, instead of only parsing a whole input. Please add `Lark.scan(text, start=None)`, which scans `text` (a `str`, `bytes`, or a `TextSlice`, in which case only the slice is scanned and positions stay relative to the whole text) and yields non-overlapping matches in order. Each match is a `ScanMatch`, a new class importable from `lark`, with two fields, `range` (a `(start, end)` tuple of offsets into the text) and `value`, which compares equal by value, so that `ScanMatch((1, 3), Tree('expr', []))` works, and is generic in the value type for type checking (`Lark[T].scan(...)` is an iterable of `ScanMatch[T]`). `value` is the parse tree, or what the `transformer` returns when one was given; it matches what `parse()` gives for that text, for the options `keep_all_tokens`, `maybe_placeholders` and `propagate_positions` as well (line, column and end positions refer to the whole text).

Behaviour:
- A match is the longest prefix that parses from the earliest position where one starts: `(a)(b) || (c)(d(e)` with `start: expr+` gives `(0, 6)`, then `(10, 13)`, then skips the unclosed `(d` and gives `(e)`. Text that does not parse is skipped, never raised. Matches may be adjacent. A match never starts or ends with an ignored terminal (`%ignore`), and an empty match is never produced, so a nullable start rule yields only non-empty matches and a grammar that can only match nothing yields no matches and does not loop.
- It must work with the contextual lexer and also with `lexer='basic'` (including keyword terminals that are folded into a broader terminal like `NAME`: they are still found and typed as `parse()` would). An `%ignore` pattern that merely contains the start of a match must not hide it.
- With several start symbols, `start` is required and scopes the scan to that rule; leaving it out is a `ConfigurationError`.
- Configurations that cannot scan raise `ConfigurationError` at the call of `scan()` itself, not when the generator is first iterated: any parser other than `'lalr'`, a lexer-only Lark (`parser=None`), a `postlex` (the message mentions postlex), and a custom lexer.
- User `lexer_callbacks` and the transformer may run during the search, so for the regions that do not end up matching they may be called and their results thrown away; the transformer's (and `lexer_callbacks`') results must be applied only to the match that is returned, and a transformer whose values cannot be deep-copied must still work. A callback raising `ValueError` means "this is not a valid token": that candidate is skipped and scanning goes on. Any other exception, including `ConfigurationError`, propagates. A callback returning a token without source positions (a fresh `Token` instead of `t.update(...)`) is a `LexError` whose message contains "did not preserve token positions", also when it is an earlier token rather than the last one.
- It must also be available on parsers generated by the standalone tool (`Lark_StandAlone().scan('xxaa yy a')` for `start: "a"+` gives ranges `(2, 4)` and `(8, 9)`).
- `Token` copies made by `copy.deepcopy` or pickle must keep `end_line`, `end_column` and `end_pos` along with the start position.

Please build this.
